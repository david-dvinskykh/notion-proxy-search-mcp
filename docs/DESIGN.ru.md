# Прокси-поиск по Notion: почему именно так

Документ отвечает на два вопроса: почему поиск сделан своим, а не собран из
готовых частей, и что из этого получается на четырёхъядерной ARM-плате с 8 ГБ
памяти (Raspberry Pi 4B).

Все числа ниже — замеры на настоящих весах и на настоящем корпусе, если прямо не
сказано иное. Пересчёт на Pi — единственная оценка, и она помечена как оценка.

## 1. Задача

Официальный MCP-сервер Notion упирается в три ограничения, и все три мешают
агенту, который читает базу знаний на каждом шаге:

- **квоты на чтение** — поиск и SQL уходят в сеть и считаются в лимит воркспейса;
- **один источник на запрос** — join между базами либо недоступен, либо за
  платным планом;
- **поиск по ключевым словам** — для русского и украинского это означает, что
  перефразированный вопрос не находит ответ, потому что у слов другая форма.

Прокси снимает все три: держит зеркало в SQLite, отдаёт по нему SQL без квот и
ищет гибридно — эмбеддинги плюс BM25.

## 2. Почему не готовые решения

| Вариант | Почему не он |
| --- | --- |
| Официальный Notion MCP как есть | Те самые три ограничения из §1 — они и были поводом |
| Zep / Graphiti | Отдельный сервис плюс Postgres (у Graphiti — Neo4j). Семантику записи (би-темпоральность, инвалидация) в этой системе уже обеспечивает сама база Notion; платить за неё вторым хранилищем незачем, а по памяти это не влезает рядом с остальными контейнерами платы |
| Mem0 | В 2026-м отказался от UPDATE/DELETE вовсе (ADD-only, противоречия разрешаются ранжированием при чтении). Здесь нужна обратная модель: опровержение — явная операция со своими полями |
| Letta | Агентный фреймворк целиком; нужен был ретривер, а не второй агент |
| Qdrant / Chroma / Milvus | Отдельный сервер на 300–700 МБ RSS ради нескольких тысяч векторов. Плоский перебор 6 000 × 384 байта — это 2,3 МБ и единицы миллисекунд; ANN-индекс начинает оправдываться на порядок выше |
| `sqlite-vec` / `sqlite-vss` | Расширение на C: нужен cgo, кросс-компиляция под arm64 усложняется, а выигрыша над перебором на этом размере нет |
| Ollama / llama.cpp как сервер эмбеддингов | Второй процесс, cgo, +300 МБ, и модель на 300M параметров в Q4 примерно в десять раз дороже по CPU, чем выбранная (§4) |
| text-embeddings-inference (Rust) | Снова отдельный сервис; arm64-образ тяжёлый, выигрыш по качеству нулевой при той же модели |
| ONNX Runtime через cgo | Самый серьёзный кандидат: проверенная численность, int8-ядра под ARM. Отклонён из-за стоимости сборки (кросс-тулчейн плюс `libonnxruntime.so` ~15 МБ в образ). Цена отказа измерена против самого `onnxruntime` на том же чекпойнте: худший косинус 0,99811 (§4) |

## 3. Архитектура

```
                    ┌─────────────────────────────────────────┐
  Notion REST  ───▶  │ daemon (один на хост)                   │
  (только чтение)    │  • опрос: data source query по watermark│
                     │  • сверка раз в 6 ч: замечает удаления  │
                     │  • блоки → Markdown                     │
                     │  • чанки → FTS5 + int8-векторы          │
                     │  • модель: mmap, один экземпляр         │
                     └──────────┬────────────────┬─────────────┘
                                │ unix socket    │ SQLite (WAL)
                                │ (только поиск  │
                                │  и resync)     ▼
                     ┌──────────▼───────────┐  mirror.db
  MCP-клиент ─stdio─▶│ serve (на сессию)    │  • pages / page_props
                     │  • SQL, fetch, BM25  │  • relations
                     │    локально          │  • chunks + chunks_fts
                     │  • вектор → демону   │  • vectors (int8)
                     └──────────────────────┘  • view "collection://<id>"
```

Запись в Notion идёт мимо прокси — через официальный сервер. Прокси читает;
`notion-resync` существует ровно для случая «только что записал, следующий
запрос должен это увидеть» — он не ждёт следующего опроса.

**Почему два процесса, а не один.** MCP-клиент поднимает stdio-сервер на каждую
сессию и убивает его по её окончании. Если модель грузить в stdio-процесс, на
трёх параллельных сессиях это три копии весов и три холодных старта; зеркало
тоже умирало бы вместе с сессией. Демон переживает сессии, держит веса один раз
и сам поднимается из первого `serve` (`setsid`, лог в `daemon.log`), так что в
конфигурации клиента по-прежнему одна stdio-команда.

**Деградация вместо отказа.** Если демон не отвечает, `notion-search` выполняет
только BM25 и пишет в ответ поле `degraded` с причиной, а не молча отдаёт худший
результат.

## 4. Модель эмбеддингов и квантование

### Выбор модели

Требования: русский, украинский, польский и английский в одном пространстве;
≤ 150 МБ на диске; и — главное — стоимость одного прохода, потому что
индексировать придётся тысячи чанков на четырёх ядрах Cortex-A72.

Стоимость прохода считается точно: на каждый токен энкодер делает
`L × (4·H² + 2·H·I)` умножений-с-накоплением. Для 12 слоёв, H = 384, I = 1536
это **21,2 MMAC на токен** — расчёт, который замер потом подтвердил с точностью
до процентов.

| Модель | Параметры | int8 на диске | MMAC/токен | Почему / почему нет |
| --- | --- | --- | --- | --- |
| **multilingual-e5-small** | 118M (из них 96M — таблица эмбеддингов) | **118,7 МБ** (замерено) | **21** | Выбрана. 12 слоёв × 384; 100+ языков; вычислений мало, потому что почти весь вес — таблица токенов, а не слои |
| paraphrase-multilingual-MiniLM-L12-v2 | 118M | ~118 МБ | 21 | Та же цена, заметно слабее на retrieval-задачах |
| multilingual-e5-base | 278M | ~278 МБ | 85 | В четыре раза дороже по CPU за несколько пунктов качества |
| LaBSE | 471M | ~470 МБ | 85 | Заточена под bitext mining, не под поиск |
| bge-m3 | 568M | ~570 МБ | 170 | Сильнейшая из мультиязычных и полностью неподъёмная: восемь раз по цене выбранной |
| EmbeddingGemma-300M | 300M | ~200 МБ (Q4, QAT) | ~200 | Спроектирована под устройства и умеет Matryoshka (768→128). Но 24 слоя × 768 — это на порядок больше арифметики; на A72 один чанк уходил бы в десяток секунд |

### Измеренная производительность

Сначала микро-бенчмарки ядер (x86-64, Xeon 2,8 ГГц, 4 ядра; `make bench`):

| Что | Результат |
| --- | --- |
| `dotI8`, 384 элемента | 126 нс → **3,05 GMAC/с** на ядро |
| `linear` 384×1536, 32 токена, 1 воркер | 15,3 мс → 1,23 GMAC/с |
| `linear` 384×1536, 32 токена, 4 воркера | 4,06 мс → **4,65 GMAC/с**, масштабирование близко к линейному |

Затем настоящая модель на настоящих весах (`make bench-model`, те же 4 ядра):

| Токенов | 4 воркера | 1 воркер |
| --- | --- | --- |
| 19 | 102 мс | 266 мс |
| 43 | 219 мс | 550 мс |
| 131 | 724 мс | 1 725 мс |
| 259 | 1 721 мс | 3 708 мс |

Пропускная способность держится около **185 токенов/с на четырёх ядрах** и
падает к длинным последовательностям (квадратичное внимание плюс промахи кеша).

Две находки, из-за которых код выглядит так, как выглядит:

1. **Ручная развёртка цикла делает хуже втрое.** Вариант с четырьмя и восемью
   независимыми аккумуляторами дал 373 и 348 нс против 126 нс у простого
   `for i, x := range a` с `b = b[:len(a)]`. Развёртка ломает компилятору и
   векторизацию, и устранение проверок границ. В коде стоит комментарий и
   бенчмарк как арбитр — чтобы это не «оптимизировали» обратно.
2. **Тайлинг выходов важнее всего остального.** Запись `out[t*rows+o]` с
   индексом выхода во внутреннем цикле трогает по одной кеш-линии на каждый
   токен; если тайлить выходы и держать цикл по токенам снаружи тайла, записи
   идут подряд: 28,2 → 15,3 мс на одном ядре. Ширина тайла 128 — лучшее из
   16/32/64/128/256/384.

### Память — замерена, а не оценена

| Что | Сколько |
| --- | --- |
| Весовой блоб на диске | **118,7 МБ** (из 470 МБ float32) |
| Конвертация checkpoint → блоб | 5,4 с |
| Пиковый RSS при счёте эмбеддингов | **115 МБ**, из них **104 МБ — отображённый файл** |
| Анонимная (настоящая приватная) память | ≈ 11 МБ |
| Демон в покое, модель ещё не тронута | 4,8 МБ |

Главное здесь — 104 из 115 МБ это страницы файла: они делятся между любым
числом процессов и вытесняются под давлением. Приватная цена демона — порядка
десятка мегабайт.

### Три уровня квантования

**1. Веса — int8 с масштабом на строку.** Каждая матрица хранится как int8 плюс
`float32`-масштаб на каждую строку выхода. Один масштаб на всю матрицу теряет
несколько процентов: выходные каналы attention-проекций различаются по амплитуде
на порядок. Гранулярность по строке — самая дешёвая схема, которая держится в
пределах пары процентов от float (`TestLinearApproximatesFloatMatmul`).

Таблица эмбеддингов (250 037 × 384 — почти вся модель) квантуется так же. Это
безопасно: лукап одной строки никогда не попадает в накопление с другими, ошибка
не копится.

LayerNorm, смещения и финальная нормализация остаются `float32` — они стоят
копейки по памяти и заметны по качеству.

**2. Активации — динамически, на токен.** Перед каждым умножением строка
активаций квантуется в int8 со своим масштабом. Динамическая схема выбрана не
от бедности: статическая требует калибровочного корпуса, а русско-украинского
калибровочного набора под эту модель нет, и собирать его ради 10 % скорости —
плохая сделка. Результат разворачивается одним умножением на элемент:
`acc · scale_веса[o] · scale_активации[t]`.

**3. Хранимые векторы — int8 с одним масштабом на вектор.** Вектор нормирован,
поэтому косинус — это скалярное произведение, а скалярное произведение двух
int8-векторов считается в int32. Вчетверо меньше памяти и вчетверо быстрее
перебор; дрейф похожести измерен и держится в пределах 0,01.

Чего сознательно нет:

- **int4 по весам.** В Go без SIMD распаковка полубайтов съедает больше, чем
  экономит на пропускной способности памяти: узкое место здесь — целочисленные
  операции, а не чтение весов. Плюс заметная потеря качества на 12-слойной
  модели;
- **бинарное (1-битное) квантование векторов.** Даёт 32-кратную экономию и имеет
  смысл как первый проход на сотнях тысяч векторов; на нескольких тысячах
  экономить 2,3 МБ незачем;
- **Matryoshka-усечение размерности.** Параметр `-dim` у конвертера есть, но
  e5-small не обучалась с MRL, и обрезание 384→256 у неё просто теряет
  информацию. Усечение оправдано только на моделях, обученных с ним;
- **квантование attention-матрицы (Q·Kᵗ и P·V).** T² арифметики при T ≤ 512 —
  доли процента от общего счёта; оставлены в float32, где они точнее.

### Чем проверена своя реализация

Три проверки, все закреплены тестами и все требуют блоба (`NPS_TEST_MODEL`); без
него они пропускаются.

**Токенизатор — точное совпадение.** В `internal/embed/testdata/tokenizer_golden.json`
лежат 448 эталонных сегментаций, снятых библиотекой `tokenizers` с того самого
`tokenizer.json`: русский, украинский, польский, английский, SQL-фрагменты,
эмодзи, смешанные скрипты, полноширинные символы, неразрывные и нулевой ширины
пробелы, плюс весь текст этого документа и README построчно. Go-токенизатор
совпадает со всеми. Это не было так с первого раза — сверка нашла четыре ошибки,
каждую из которых невозможно было заметить без эталона:

1. концевой пробел отбрасывался, а SentencePiece оставляет его отдельным куском;
2. строка из одних пробелов давала ноль кусков вместо одного;
3. нулевой ширины пробелы (U+200B/200C/200D, BOM) считались текстом и уходили в
   `<unk>`, а эталон делает из них границу слова;
4. служебные строки чекпойнта (`<mask>`, `<unk>`, `<s>`, `</s>`, `<pad>`),
   встреченные в тексте буквально, сегментировались как обычные символы. Эталон
   режет вход по ним **до** нормализации и отдаёт за каждую один id, а каждый
   отрезок нормализует отдельно — со своим ведущим `▁`. Теперь таблица этих
   строк лежит в блобе (`added_tokens` в заголовке), и `Encode` делает тот же
   разрез: `a<mask>b` → `▁a`, `<mask>`, `▁b`.

Осталось два расхождения, оба сознательные и закреплены отдельным тестом: байт
NUL эталон превращает в `<unk>` и границу, NEL (U+0085) держит отдельным куском —
здесь оба отбрасываются вместе с остальными управляющими. Через JSON-API Notion
такой символ до зеркала не доходит.

**Численность — косинус 0,998 против float32.** Эталон считает `onnxruntime` на
том же чекпойнте (`onnx/model.onnx`, 470 МБ float32), который с Go-реализацией не
делит ни строки кода, только веса. На 21 случае (вопросы и пассажи на четырёх
языках, эмодзи, SQL, один символ, текст из 120 слов) **худший косинус — 0,99811**
(на слове «бетон»: чем короче текст, тем меньше токенов усредняется и тем
заметнее шум квантования).

Порядок кандидатов для каждого запроса совпадает на первом месте. Глубже (места
2–3) сравнение требовательнее: переставить кандидатов можно только там, где сам
float32-эталон разделял их меньше чем на 0,01 — мерой взята разница эталонных
оценок того кандидата, который должен стоять на этом месте, и того, который туда
попал. На всём наборе такая перестановка одна.

## 5. Качество поиска — замер на живом корпусе

Корпус: 45 коротких фактов из рабочей базы знаний (инфраструктура и выкатка,
учёт, бытовая автоматика, техника, документы) и 49 вопросов — 37 на естественном
языке, как их задал бы человек, и 12 на точный идентификатор (имя переменной
окружения, имя куки, код шага, идентификатор чата, сумма с копейками). Прогон —
`TestRetrievalQualityOnCorpus`; корпус в репозиторий не положен, он рабочий, тест
берёт путь из переменных окружения.

| Режим | hit@1 | hit@3 | Медиана запроса |
| --- | --- | --- | --- |
| keyword (BM25) | 63 % | 78 % | **0,55 мс** |
| vector | 84 % | 98 % | 74 мс |
| **hybrid** | **86 %** | **98 %** | 73 мс |

Три вывода, которых не было до замера:

1. **Вектор бьёт BM25 с большим отрывом** — 84 % против 63 % на первом месте. Для
   русского с украинским это ожидаемо (морфология, перефразировки), но масштаб
   разрыва виден только на замере, и он оправдывает всю возню с собственным
   энкодером.
2. **Обычный RRF оказался хуже, чем одна его ветвь.** Равновесное слияние дало
   78 % / 95 % — ниже чистого вектора (84 % / 98 %). Причина арифметическая:
   мусорный keyword-хит на первом месте получает 1/61 и обгоняет правильный
   вектор-хит на третьем (1/63). Ветвь слабее тянула сильную вниз. Исправлено
   весами (вектор 1,0, keyword 0,35); свип по весам и объяснение выбора — в
   комментарии к константам в `internal/index/search.go`. После правки гибрид
   стал лучше обеих ветвей, и у теста есть соответствующий гейт.
3. **Точные идентификаторы — 12 из 12 при любом весе.** Именно поэтому keyword не
   выброшен: эмбеддинги не обязаны помнить имя куки.

Задержка запроса в векторном режиме — это почти целиком эмбеддинг самого запроса
(перебор нескольких тысяч векторов занимает микросекунды). На Pi это будет
200–300 мс на запрос; BM25 отвечает за доли миллисекунды и работает с первой
минуты, пока эмбеддинги ещё считаются.

## 6. Реальное время

Notion отдаёт изменения двумя способами, и они не равноценны:

- **`POST /v1/data_sources/{id}/query` с фильтром по `last_edited_time`** —
  строго согласован, отдаёт правку сразу. Это основной канал: по каждой базе
  хранится watermark, запрос идёт от него минус две минуты (фильтры Notion имеют
  минутную гранулярность, без запаса правка внутри той же минуты теряется);
- **`POST /v1/search`** — индекс с задержкой, иногда минуты. Используется только
  для страниц вне баз, где другого способа нет.

Опрос раз в 30 секунд при корпусе в пару тысяч страниц — это около двадцати
запросов за цикл при лимите Notion в три запроса в секунду, то есть меньше
четверти бюджета. Удаление не видно ни одному инкрементальному запросу, поэтому
раз в 6 часов идёт полная сверка состава: пропавшие строки получают
`in_trash = 1` и уходят из `collection://`-вида, но из базы не удаляются —
история сохраняется.

Вебхуков нет намеренно: они дали бы секунды вместо тридцати, но требуют
HTTP-слушателя в процессе, а сервер сделан stdio-only. Если понадобится — это
отдельный режим демона, зеркало и индекс менять не придётся.

## 7. Бюджет Pi 4B и честный срок индексации

### Память и диск

| Что | Сколько | Примечание |
| --- | --- | --- |
| Весовой блоб на диске | 118,7 МБ | int8, лежит в образе |
| Пиковый RSS демона при счёте | 115 МБ | из них 104 МБ — страницы файла, общие и вытесняемые |
| Приватная память демона | ≈ 11 МБ | замерено как RssAnon |
| Демон в покое | 4,8 МБ | веса ещё не тронуты, страницы не подняты |
| Зеркало SQLite | 40–80 МБ | текст страниц + FTS5 + чанки |
| Векторы | ≈ 0,4 МБ на 1 000 чанков | 384 байта на вектор |
| Бинарь | 9,9 МБ | статический arm64, `CGO_ENABLED=0`, кросс-компиляция без эмуляции |
| CPU в простое | близко к нулю | опрос — сеть, не счёт |

### Срок первичной индексации

Главный сюрприз замеров: **корпус неоднороден**. В типичной базе знаний есть
одна журнальная база, куда каждый день дописывается лог, и её страницы на
порядки больше остальных — замеренная карточка одного дня весила **135 799
знаков ≈ 48 500 токенов**, а сотня таких карточек даёт порядка 1,7 млн токенов
против примерно 250 тысяч во всех остальных базах вместе.

При замеренных 185 токенах/с на четырёх x86-ядрах и пересчёте на A72
(per-core примерно в 2,5 раза медленнее):

| Что индексируем | Токенов | Pi, 4 воркера | Pi, 2 воркера |
| --- | --- | --- | --- |
| Все базы, кроме журнальной | ≈ 250 тыс. | **≈ 1 час** | **≈ 2 часа** |
| Плюс журнальная база | + 1,7 млн и более | +7 часов и более | +15 часов и более |

Отсюда три решения в коде:

1. **Заголовок не дублируется в чанке.** У строки базы заголовок и есть
   утверждение, а он попадал в чанк трижды: как заголовок, как строка дайджеста
   свойств и иногда в теле. Цена чанка факта упала с 655 до **310 мс** — вдвое,
   и ровно вдвое сократился весь счёт по коротким базам.
2. **Очередь эмбеддингов идёт от самых дешёвых страниц.** Сортировка по размеру
   страницы, а не по id: сотни однострочных записей досчитываются раньше, чем
   начнётся первая гигантская страница журнала. Индекс становится полезным в
   первые минуты прогона, который целиком идёт часы.
3. **Есть явный отказ от бесполезной массы** — `NPS_EMBED_SKIP_SOURCES`.
   Исключённая база остаётся в зеркале, в SQL и в BM25, её просто не гонят через
   модель.

**Рекомендация для такой формы корпуса:** исключить журнальную базу из векторного
индекса. Её страницы ищут по дате и по точной строке — и то и другое делают SQL и
BM25. Это превращает пятнадцать часов в два, не теряя ни одного ответа, который
дал бы эмбеддинг. Снять исключение можно в любой момент — остаток досчитается
фоном.

## 8. Ограничения — честно

1. **Два расхождения токенизатора сознательные:** байт NUL и NEL (U+0085) здесь
   отбрасываются, эталон делает из первого `<unk>`, а второй держит отдельным
   куском. Через JSON-API Notion такие символы до зеркала не доходят; тест это
   фиксирует, а не прячет.
2. **Реранкера нет.** Cross-encoder на 30 кандидатов стоит дороже, чем весь
   остальной запрос, на этом железе. Качество топа держат веса колонок BM25,
   веса ветвей при слиянии и дедупликация по странице; замер говорит, что этого
   хватает: 86 % hit@1 и 98 % hit@3.
3. **Оценка качества — 49 вопросов на 45 фактах.** Этого достаточно, чтобы
   поймать грубое (и она поймала: равновесный RRF), но мало, чтобы тонко
   настраивать веса. Прогон на полном корпусе — после первой индексации.
4. **Вебхуков нет** (§6). Задержка — до 30 секунд, `notion-resync` закрывает
   случай «нужно сейчас».
5. **Сервер ещё не говорил с живым API Notion.** Все его запросы проверены против
   поддельного сервера в тестах: пагинация, watermark с запасом, сверка удалений,
   ретраи на 429. Первый живой обход будет на плате; в нём вероятны сюрпризы в
   схемах конкретных баз, и лечиться они будут как обычные баги.
6. **Запись не поддерживается и не планируется.** Это осознанная граница:
   правки идут через официальный сервер, у прокси нет ни одного инструмента,
   меняющего Notion.
7. **Rollup отдаётся значением, а не `rollupResult://`-ссылкой**, а relation —
   JSON-массивом id. Расхождение с официальным сервером в сторону большей
   информативности; знать об этом стоит.

## 9. Развёртывание

1. **Интеграция Notion.** notion.so/my-integrations → Internal integration,
   capabilities только на чтение. Затем расшарить с ней корневую страницу базы
   знаний: Notion даёт доступ по страницам, нерасшаренное прокси не видит.
   Подстраницы и базы наследуют доступ от корня.
2. **Регистрация сервера** в MCP-клиенте или шлюзе как stdio-команда:

   ```json
   {
     "name": "notion-proxy-search",
     "type": "STDIO",
     "command": "notion-proxy-search-mcp",
     "args": [],
     "env": {
       "NOTION_TOKEN": "<секрет интеграции>",
       "NPS_EMBED_WORKERS": "2",
       "NPS_EMBED_SKIP_SOURCES": "<id журнальной базы>"
     }
   }
   ```

   `NPS_EMBED_WORKERS=2` оставляет половину ядер остальным процессам платы на
   время первичной индексации; после неё ограничение можно снять.
   `NPS_EMBED_SKIP_SOURCES` — по причине из §7.

Первый запуск: `serve` поднимает демона, демон делает bootstrap-обход (минуты,
зависит от числа страниц), затем фоном считает эмбеддинги — от самых дешёвых
страниц к самым дорогим. До их готовности поиск работает в режиме BM25 и сам
сообщает об этом в поле `degraded`. Прогресс видно в `notion-mirror-status`
(`pending_vectors`, `cached_vectors`, `not_embedded`).
